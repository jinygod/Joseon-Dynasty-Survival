# 조선 왕조 서바이벌 전체 개발·출시 운영 설계

## 1. 목표

현재 5분 싱글플레이 알파를 Android 1.0 제품으로 완성하고, 비공개 테스트·스토어 심사·정식 출시·초기 안정화까지 하나의 순서 있는 실행 체계로 관리한다.

이 문서는 게임 세계관이나 전체 스토리 시나리오가 아니라 앱 개발과 출시의 전체 시나리오를 정의한다. 구체적인 실행 항목은 별도의 마스터 TODO 문서에서 체크박스로 추적한다.

## 2. 현재 기준선

2026-07-14 기준:

- `master`에 5분 싱글플레이 세로 슬라이스가 통합되어 있다.
- 웨이브, 일반 적 4종, 보스 1종, 무기 4종, 증강, 레벨업, 결과 화면, 해금·저장 시스템이 연결되어 있다.
- 정적 분석은 문제 없이 통과한다.
- 자동 테스트 82개가 통과한다.
- 웹 릴리스 빌드가 통과한다.
- GitHub Actions와 로컬 릴리스 검증 스크립트가 있다.
- 최종 게임 이미지 자산과 오디오 자산은 아직 없다.
- 모바일 조작, 설정, 튜토리얼, 출시 콘텐츠, 실제 기기 QA, Android 릴리스 서명과 스토어 자료가 남아 있다.

## 3. 운영 방식

### 품질 게이트형 순차 개발

개발은 12개 단계로 진행한다. 단계마다 선행조건, 작업 목록, 자동 검증, 수동 QA, 완료 게이트를 둔다. 현재 단계의 완료 게이트를 통과하기 전에는 다음 단계의 대량 콘텐츠 제작을 시작하지 않는다.

일부 준비 작업은 병렬로 할 수 있지만 다음 규칙을 지킨다.

- 아트 콘셉트 조사와 라이선스 목록 준비는 코어 재미 검증 중에 가능하다.
- 최종 자산 대량 제작은 플레이어·적·무기 실루엣과 전투 가독성 기준이 승인된 뒤 시작한다.
- 스토어 계정과 법적 자료 준비는 안정화 전에 시작할 수 있다.
- 스토어 제출용 스크린샷과 트레일러는 최종 UI와 아트가 잠긴 뒤 제작한다.
- 신규 캐릭터·무기·스테이지는 기존 5분 런의 재미 게이트 통과 후 확장한다.

## 4. 상태와 책임 표기

모든 마스터 TODO 항목은 다음 정보를 가진다.

- 상태: `완료`, `진행 중`, `대기`, `차단`, `제외`
- 우선순위: `P0`, `P1`, `P2`, `P3`
- 책임: `Codex`, `사용자`, `공동`
- 선행조건: 먼저 끝나야 하는 작업 ID
- 산출물: 코드, 테스트, 문서, 이미지, 음원, 계정 또는 스토어 자료
- 검증: 실행 명령 또는 수동 확인 절차
- 완료 기준: 다음 단계로 넘어갈 수 있는 객관적 조건

`차단` 상태는 계정, 실기기, 외부 테스터, 법적 정보처럼 사용자 또는 외부 환경이 반드시 필요한 경우에만 사용한다. 차단되지 않은 Codex 담당 작업은 순서대로 계속 진행한다.

## 5. 전체 단계

### 단계 1 — 제품 방향과 1.0 범위 확정

목적은 개발 중 범위가 계속 늘어나는 일을 막는 것이다.

확정 항목:

- 1차 플랫폼: Android
- 지원 방향: 가로 화면
- 핵심 모드: 싱글플레이 생존 런
- 네트워크 없는 오프라인 플레이
- 플레이테스트 기록: 기기 내부 저장과 JSON 복사·내보내기
- 1.0 제외: 온라인 협동, 광고, 인앱 결제, 일일 과제, 라이브 서비스
- iOS와 Windows/Steam: Android 1.0 이후 별도 트랙

완료 게이트: 제품 한 문장 설명, 대상 사용자, 주력 런 길이, 최소 출시 콘텐츠, 제외 범위가 문서에서 모순 없이 확정되어야 한다.

### 단계 2 — 개발 환경·CI·저장 기반

목적은 모든 이후 변경을 재현 가능하고 안전하게 검증하는 것이다.

범위:

- Flutter 버전과 의존성 고정
- 로컬 한 명령 릴리스 게이트
- GitHub Actions 분석·테스트·웹·Android 빌드
- 저장 스키마 버전과 마이그레이션
- 버전명·빌드 번호 규칙
- 오류 로그와 개발용 진단 정보

완료 게이트: 깨끗한 영문 경로 환경에서 분석, 전체 테스트, 웹 빌드, Android 디버그 빌드가 자동으로 통과하고 저장 데이터 업그레이드 테스트가 있어야 한다.

### 단계 3 — 플레이테스트 기록과 코어 재미 검증

목적은 감으로 밸런스를 바꾸지 않고 실제 런 데이터를 기준으로 판단하는 것이다.

수집 데이터:

- 런 ID와 앱 버전
- 결과, 생존 시간, 도달 레벨, 처치 수, 보스 처치 여부
- 무기별 레벨, 피해량, 처치 수
- 증강과 무기 선택 순서
- 플레이어가 받은 총 피해와 사망 시점
- 플레이테스터의 재미 점수, 난이도 점수, 재도전 의사, 짧은 의견

데이터는 서버로 전송하지 않는다. 기기 내부에 최근 50개 런을 저장하고 결과 화면에서 단일 런 또는 전체 기록을 JSON으로 복사·내보낼 수 있게 한다. 저장 실패가 게임 결과나 진행 저장을 막아서는 안 된다.

완료 게이트: 내부 20런과 외부 테스터 10명 이상의 기록을 같은 형식으로 수집할 수 있고, 첫 판 완료율·재도전 의사·무기별 성과·주요 사망 구간을 계산할 수 있어야 한다.

### 단계 4 — 모바일 조작과 전체 게임 흐름

목적은 처음 설치한 사용자가 별도 설명 없이 한 판을 완료하게 하는 것이다.

범위:

- 실제 모바일 가상 스틱
- 입력 해제와 앱 백그라운드 전환 처리
- 일시정지, 재시작, 메인 메뉴 복귀
- 첫 실행 튜토리얼
- 캐릭터·스테이지 선택의 최소 흐름
- 결과, 재도전, 해금 확인
- 화면 비율과 안전 영역 대응

완료 게이트: 지원 화면 비율에서 UI가 잘리지 않고, 신규 사용자의 80% 이상이 도움 없이 첫 판 결과 화면까지 도달해야 한다.

### 단계 5 — 전투 손맛과 밸런스

목적은 5분 런 자체를 반복하고 싶은 수준으로 만드는 것이다.

범위:

- 초반 학습, 중반 빌드 형성, 후반 압박, 보스 결전 리듬
- 무기·증강 선택의 실제 차이
- 적 체력, 수, 피해량, 이동 속도, 경험치 곡선
- 피격 무적 시간, 넉백, 화면 흔들림, 피해 숫자
- 보스 경고와 회피 가능성
- 고정 시드 밸런스 회귀 테스트

완료 게이트: 외부 플레이테스터의 60% 이상이 즉시 재도전 의사를 보이고, 특정 무기 하나가 선택률과 승률을 독점하지 않으며, 억울한 피격이 반복 재현되지 않아야 한다.

### 단계 6 — 최종 아트와 애니메이션

목적은 임시 도형을 일관된 조선 민속 판타지 비주얼로 교체하는 것이다.

범위:

- 아트 스타일 가이드와 팔레트
- 플레이어, 일반 적, 보스 스프라이트와 애니메이션
- 무기, 투사체, 범위, 피격, 사망 효과
- 스테이지 타일과 배경 장식
- HUD, 아이콘, 메뉴, 레벨업, 결과 화면
- 자산 출처, 생성 기록, 라이선스 장부

완료 게이트: 모든 임시 도형과 개발자용 시각물이 제거되고, 한 화면 캡처에서 플레이어·적·위험·경험치·공격 유형을 설명 없이 구분할 수 있어야 한다.

### 단계 7 — 음악·효과음·햅틱

목적은 전투 상태를 소리와 진동으로도 명확하게 전달하는 것이다.

범위:

- 일반 전투, 보스전, 승리, 패배 음악
- 무기 4종 이상 공격음
- 피격, 치명타, 사망, 경험치, 레벨업, 경고, UI 효과음
- 동시 발음 제한과 반복음 변화
- 음악·효과음·진동 개별 설정과 저장

완료 게이트: 공격 성공, 피격, 레벨업, 보스 위험, 승패를 화면 없이도 구분할 수 있고 저사양 기기에서 음향 때문에 프레임이 끊기지 않아야 한다.

### 단계 8 — 출시 콘텐츠

목적은 반복 플레이와 해금 동기를 제공하는 최소 1.0 볼륨을 완성하는 것이다.

권장 최소 범위:

- 캐릭터 3명
- 무기 8종
- 증강 16종 이상
- 일반 적 8종 이상
- 엘리트 변형 3종 이상
- 스테이지 2개
- 보스 3종
- 해금 목표 15개 이상

각 콘텐츠는 수치만 다른 복제가 아니라 플레이 판단을 바꾸는 역할이 있어야 한다.

완료 게이트: 모든 콘텐츠가 최종 자산·효과음·설명·해금 조건·자동 테스트를 갖추고, 최소 세 가지 이상 유효한 빌드 조합이 존재해야 한다.

### 단계 9 — 메타 진행·설정·접근성

목적은 런 밖의 제품 경험과 장기 진행을 완성하는 것이다.

범위:

- 캐릭터·무기·증강 도감과 해금 조건
- 최고 기록과 캐릭터별 기록
- 설정 화면과 저장
- UI 크기, 화면 흔들림, 피해 숫자, 색 외 구분 수단
- 크레딧, 라이선스, 진행 초기화 확인
- 저장 손상 복구와 사용자 안내

완료 게이트: 모든 설정과 진행 데이터가 재실행·업데이트 후 유지되고, 저장 손상과 초기화 경로가 검증되어야 한다.

### 단계 10 — 성능 최적화와 QA

목적은 목표 Android 기기에서 안정적인 1.0 후보를 만드는 것이다.

범위:

- 최소·보급형·중급형·고급형 기기 매트릭스
- 16:9, 18:9, 19.5:9, 태블릿 화면
- 60 FPS 목표와 프레임·메모리·발열·배터리 측정
- 컴포넌트·적·투사체·이펙트 성능 예산
- 앱 전환, 전화, 알림, 잠금, 저메모리, 강제 종료
- 신규 설치, 업데이트, 재설치, 오프라인, 저장 복구
- 통합 테스트, 골든 테스트, 장시간 반복 테스트

완료 게이트: 크래시, 진행 불가, 저장 소실, 입력 불가, 보이지 않는 공격이 0건이고 목표 기기 성능 예산을 통과해야 한다.

### 단계 11 — Android 출시와 소프트 론치

목적은 검증된 빌드를 실제 스토어 배포 가능한 제품으로 전환하는 것이다.

범위:

- 최종 앱 이름과 application ID
- 릴리스 키와 AAB 서명
- 아이콘, 스플래시, 스토어 설명, 스크린샷, 트레일러
- 개발자 계정, 지원 연락처, 개인정보처리방침
- 데이터 안전성, 연령 등급, 라이선스와 상표 확인
- 내부 테스트와 비공개 테스트 트랙
- 크래시, ANR, 첫 판 진입, 완주, 재도전 지표

완료 게이트: 크래시 없는 사용자 99.5% 이상, 첫 판 진입 90% 이상, 결과 화면 도달 75% 이상, 두 번째 판 진입 50% 이상, 저장 소실 0건을 만족해야 한다.

### 단계 12 — 정식 출시와 초기 운영

목적은 1.0을 안전하게 공개하고 초기 문제를 빠르게 수습하는 것이다.

범위:

- 1.0 빌드 동결과 심사 제출
- 출시 공지, 트레일러, 커뮤니티, 프레스 자료
- 첫 72시간 크래시·리뷰·지원 문의 모니터링
- 핫픽스 브랜치와 배포 절차
- 2~4주 단위 업데이트 원칙
- Android 안정화 이후 iOS와 Windows/Steam 별도 기획

완료 게이트: 1.0이 스토어에 공개되고, 차단 버그 없이 7일을 운영하며, 첫 패치 백로그가 실제 사용자 데이터로 정리되어야 한다.

## 6. 실행 리듬

각 단계는 다음 순서로 실행한다.

1. 해당 단계의 상세 TODO와 완료 기준을 확인한다.
2. 격리 브랜치 또는 작업공간을 만든다.
3. 코드 변경은 실패하는 테스트부터 작성한다.
4. 작은 작업 단위로 구현하고 자동 검증한다.
5. 사용자 확인이 필요한 플레이·시각·음향 작업은 명시적으로 전달한다.
6. 단계 종료 시 전체 릴리스 게이트를 실행한다.
7. 변경을 기본 브랜치에 통합한다.
8. 마스터 TODO의 상태와 실제 검증 근거를 갱신한다.

한 단계가 여러 독립 하위 시스템을 포함하면 세부 구현 계획을 나누되, 마스터 TODO에서는 동일한 단계 아래에서 추적한다.

## 7. 오류와 차단 처리

- 자동 테스트 또는 빌드가 실패하면 다음 작업으로 넘어가지 않고 원인을 해결한다.
- 실기기, 스토어 계정, 서명 정보, 법적 정보가 필요한 작업은 사용자 책임으로 표시하고 준비 방법을 제공한다.
- 외부 플레이테스트 수가 부족하면 밸런스 게이트를 통과한 것으로 표시하지 않는다.
- 최종 자산의 출처나 사용 권리가 불명확하면 게임에 포함하지 않는다.
- 저장 형식을 변경할 때는 이전 버전 데이터 마이그레이션 테스트가 없으면 병합하지 않는다.
- 출시 후보 단계에서는 차단 버그 외 기능 추가를 금지한다.
