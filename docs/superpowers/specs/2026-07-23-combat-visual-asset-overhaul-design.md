# 전투 비주얼·에셋 전면 개선 설계

- 상태: 사용자 승인 설계를 문서화한 구현 전 명세
- 작성일: 2026-07-23
- 대상: Flutter + Flame 조선 민속 판타지 뱀서라이크
- 선행 문서:
  - `docs/superpowers/specs/2026-07-22-balanced-casual-art-overhaul-design.md`
  - `docs/superpowers/specs/2026-07-20-player-motion-hwando-presentation-design.md`
- 우선순위: 이 문서는 위 문서의 아트 방향을 유지하되, 전투 VFX 연결 방식, 이미지 기반 무대, 전투 에셋 계약과 성능 검증에 관해 충돌하는 임시 구현 방침을 대체한다.

## 1. 목적

현재 전투에서 원·부채꼴·선·단색 면 등 Canvas 도형이 주 시각 표현으로 남아 있는 공격과 상태 효과를 실제 PNG/스프라이트 기반 연출로 교체한다. 첫 번째 수직 완성 단위는 환도베기이며, 같은 데이터가 피해 판정과 시각 연출을 함께 구동하도록 구조를 정리한다. 이후 다른 무기 VFX, 적 VFX, 무대 타일과 장식, 누락된 적 스프라이트까지 동일한 계약으로 확장한다.

완료 결과는 다음 조건을 만족해야 한다.

- 환도베기의 기본 공격, 좌우 연계, 검기, 숙련 원형기와 마무리 연출이 도형 대신 방향성 있는 이미지 VFX로 표현된다.
- 피해 판정과 시각 연출이 서로 다른 방향·범위·타이밍을 갖지 않는다.
- 전투 도중 첫 이미지 로드와 디코딩으로 생기는 끊김을 막기 위해 필요한 전투 에셋을 선로딩한다.
- 개발 전용 VFX 갤러리에서 실제 전투 컴포넌트와 동일한 에셋·레지스트리를 검토할 수 있다.
- 무대는 정적 이미지 타일·데칼·소품으로 구성되며 매 프레임 객체를 만들지 않는다.
- 런타임 등록이 빠진 적 8종은 기존 적 이미지 복제가 아닌 고유 4×4 스프라이트 시트를 갖는다.
- 성능 수치는 결정론적 호스트 시뮬레이션과 실제 브라우저 렌더 타이밍을 구분해 보고한다.
- 게임 밸런스, 공격력, 범위, 재사용 대기시간, 적 체력과 생성 규칙은 변경하지 않는다.

## 2. 비목표

- 이번 작업에서 무기나 적의 게임 밸런스를 재설계하지 않는다.
- Flame 외에 새로운 타일맵·렌더링 패키지를 도입하지 않는다.
- 상용 게임이나 권리 불명 에셋을 복제하지 않는다.
- 단색 도형을 PNG로 저장하는 방식으로 이미지화를 완료 처리하지 않는다.
- 실제 기기 측정 없이 모바일 60 FPS 달성을 주장하지 않는다.
- 모든 UI를 한 번에 재제작하지 않는다. UI는 이미지화 공백을 감사하고 후속 우선순위를 남긴다.
- 출처와 사용 상태가 불명확한 파일을 자동 삭제하지 않는다.

## 3. 확인된 현재 상태

### 3.1 환도베기

`assets/images/effects/weapon_effects_atlas_64.png`는 256×256 크기의 4×4 아틀라스이며 각 셀은 64×64이다. 환도 행은 첫 번째 행의 4프레임이고 각 프레임에는 실제 알파 픽셀이 존재한다. `WeaponEffectAtlas`도 `srcPosition=(frame*64,row*64)`, `srcSize=64` 계약으로 이를 올바르게 자른다.

문제의 핵심은 이미지 분할이 아니라 런타임 연결이다. `MeleeArcComponent`는 스프라이트 선택과 회전을 지원하지만 `pixel_survivor_game.dart`에서 환도베기 arc를 제외한다. 환도 `AttackInstance`는 `AttackEffectComponent`로 전달되고, 이 컴포넌트가 부채꼴·원·선 Canvas 도형을 그린다. 따라서 환도 이미지가 있어도 주 연출에는 사용되지 않는다.

현재 환도 단계는 기본 베기, 좌·우 연계, 검기, 숙련 시작, 좌·우 연속기, 원형기, 마무리를 포함한다. 한 행 4프레임만으로 이 모든 형태를 명확히 표현할 수 없으므로 기본 궤적, 원형기, 검기·마무리, 타격 섬광을 별도 에셋 계약으로 분리해야 한다.

### 3.2 아직 주로 도형에 의존하는 전투 표현

- 환도베기 각 단계와 공용 `AttackInstance` 기반 베기
- 바람·번개 부채의 fallback arc
- 신기전
- 장승 오라와 수호 영역
- 서리 장판
- 오색 결계
- 부적 부착과 전이
- 적의 독, 충격파, 비명 계열 위험 효과
- 적 공격 예고
- 방패 방향과 막기
- 적 투사체

일부 전투 효과와 보스 경고에는 스프라이트와 fallback이 함께 존재한다. 이 경우 fallback이 정상 경로처럼 조용히 사용되는지 확인하고, 개발 빌드에서는 누락을 드러내도록 바꾼다.

### 3.3 누락된 적 스프라이트 등록

다음 8종은 `AssetCatalog`에서 다른 이미지를 재사용하지만 `EnemySpriteSheet.specs`에 고유 런타임 규격이 없다.

- `sakkat_specter`
- `plague_crow`
- `spear_bandit`
- `rotten_herbalist`
- `grave_ember`
- `black_hat_assassin`
- `broken_jangseung_spirit`
- `sorrowful_maiden_ghost`

현재 공통 적 애니메이션 계약은 4×4 시트이며 이동 0–3, 공격 4–7, 피격 8–9, 사망 10–15 프레임이다. 새 적도 이 계약을 지켜 기존 상태 머신과 호환한다.

### 3.4 성능 기준과 한계

기존 5분 개발 로그의 시드 3107, 18,000 프레임 기준으로 평균·최대 적 수는 15.68/51, 후반 평균·최대는 27.24/51, peak host update+lifecycle은 6,318µs였다. 기록된 60 FPS는 고정 `dt` 기반 논리 FPS이므로 실제 렌더 FPS로 보고하지 않는다.

기존 재실행은 앱 코드 진입 전 Flutter `ink_sparkle.frag` 셰이더 컴파일 중 `ShaderCompilerException`과 SIGSEGV로 실패했다. 이는 앱 성능 회귀와 분리된 개발 환경 장애로 기록한다.

현재 주요 비용 후보는 다음과 같다.

- 적 수와 생성 판단을 위한 반복적인 루트 `children` 탐색
- 투사체×적의 O(P×E) 충돌 검사
- 오라의 O(E²) 탐색
- 공유 공격의 반복 탐색, 임시 목록, 재귀 시너지 처리
- 서리·결계의 목록 할당과 적×장판 반복
- 정리 단계의 반복 필터와 스냅샷 할당
- 컴포넌트 `onLoad`에서 시작되는 비동기 이미지 로드와 첫 디코딩

## 4. 선택한 접근: 계약·갤러리 우선 수직 완성

전체 효과를 한꺼번에 등록하지 않는다. 먼저 공통 시각 이벤트와 레지스트리 계약을 만들고, 환도베기를 실제 전투까지 완성해 계약을 검증한다. 그 다음 동일한 경로로 플레이어 무기, 적 효과, 무대, 누락 적 순서로 확장한다.

이 접근은 다음 장점을 갖는다.

- 임시 에셋을 대량 등록한 뒤 런타임 계약을 다시 고치는 비용을 줄인다.
- 갤러리와 실전이 같은 컴포넌트를 사용하므로 “갤러리에서만 정상”인 가짜 완료를 방지한다.
- 방향, 피벗, 크기, 타이밍 문제를 환도 수직 단위에서 먼저 해결한다.
- 각 마일스톤의 파일 소유권과 완료 조건을 좁게 유지할 수 있다.

## 5. 전투 시각 데이터 흐름

### 5.1 권한 경계

게임플레이 계층의 `WeaponSystem`과 적 행동 시스템이 다음 값을 계속 소유한다.

- 대상 선택
- 공격 원점과 방향
- 피해 범위와 각도
- 피해량
- 재사용 대기시간
- 판정 발생 시점
- 숙련·시너지 단계

시각 계층은 이 값을 변경하거나 피해 대상을 결정하지 않는다. 시각 효과가 보이지 않거나 에셋 로드에 실패해도 피해 로직은 동일하게 실행되어야 한다.

### 5.2 불변 시각 이벤트

공격 생성 시 `AttackVisualEvent`와 동등한 불변 데이터 객체를 만든다. 최소 필드는 다음과 같다.

- 안정적인 `effectId`
- 월드 원점
- 생성 시 고정된 방향 벡터 또는 각도
- 판정 형상과 표시 범위
- `impactAt`
- 전체 `duration`
- 표현 단계 또는 숙련·시너지 변형
- 필요할 때만 쓰는 대상 위치·식별 정보

피해 판정과 VFX는 같은 공격 데이터에서 파생한다. VFX가 늦게 로드되거나 프레임이 건너뛰어져도 공격 방향과 판정은 생성 시점 값에서 달라지지 않는다.

### 5.3 시각 레지스트리

`AttackVisualRegistry`는 `effectId`를 다음 표현 계약에 연결한다.

- 에셋 경로
- 프레임 크기, 행·열, 프레임 순서
- 월드 크기와 스케일 범위
- anchor와 pivot
- 방향 변환 규칙
- 뒤·중간·앞 레이어
- 준비, 베기, 충돌, 잔상 단계의 시간 구간
- 반복 여부
- 개발 상태: `ready`, `generated-review`, `placeholder`, `missing`
- 출처와 권리 장부 키

레지스트리는 단일 출처이며 실전, 갤러리, 선로더, 계약 테스트가 함께 사용한다.

### 5.4 전문 컴포넌트

- `HwandoVfxComponent`: 방향성 베기, 숙련 원형기, 검기·마무리와 충돌 섬광을 조합한다.
- `ProjectileVfxComponent`: 투사체의 본체, 꼬리, 충돌과 소멸을 다룬다.
- `AreaVfxComponent`: 장판, 결계, 오라의 바닥·중간·상단 레이어를 다룬다.
- `EnemyTelegraphVfxComponent`: 판정 전 예고와 판정 순간 효과를 동일한 위험 영역 데이터로 표시한다.
- `StatusMarkerVfxComponent`: 부적 부착, 전이, 방패 방향처럼 개체에 붙는 상태 표시를 다룬다.

각 컴포넌트는 렌더링과 수명만 책임진다. 게임 밸런스 값이나 타격 대상 목록을 소유하지 않는다.

### 5.5 선로딩과 누락 처리

`CombatAssetPreloader`는 전투 진입 전에 현재 캐릭터·무기·스테이지·적 풀에 필요한 레지스트리 이미지를 로드하고 디코딩한다. 개별 VFX 컴포넌트는 전투 중 `images.load`를 시작하지 않고 캐시된 이미지와 스프라이트만 참조한다.

개발 빌드에서 누락된 `effectId`나 에셋은 명확한 `MISSING ASSET` 표식과 구조화 로그를 남긴다. 릴리스 빌드는 게임 진행을 막지 않는 최소한의 안전 fallback만 허용한다. fallback이 정상 완성 경로처럼 조용히 사용되어서는 안 된다.

정확한 히트박스와 공격 예고를 위한 얇고 반투명한 선은 보조 디버그·가독성 레이어로 유지할 수 있다. 단, 도형이 공격의 주 시각 표현이 되어서는 안 된다.

## 6. 환도베기 수직 완성

### 6.1 시각 단계

환도 한 번의 공격 연출은 게임플레이 판정 시간을 바꾸지 않는 범위에서 다음 네 단계로 구성한다.

1. 준비: 약 0.04–0.07초. 짧은 방향성 예광과 칼집 쪽 힘 모으기.
2. 베기: 약 0.09–0.15초. 생성 시 고정한 공격 방향을 따라 주 궤적이 빠르게 열린다.
3. 충돌: 기존 `impactAt`에 맞춰 짧은 섬광, 먹빛 파편, 적중 잔상을 표시한다.
4. 회수: 약 0.07–0.11초. 궤적이 가늘어지고 사라진다.

전체 표현은 대략 0.20–0.30초 범위에서 기존 공격 지속 시간과 판정 시점을 따른다. 이 숫자는 시각 프레임 배분 기준이며 공격 쿨다운이나 피해 판정을 변경하는 근거가 아니다.

### 6.2 에셋 묶음

환도 P0 묶음은 다음을 별도 계약으로 제작한다.

- 좌·우와 8방향 회전에 견디는 기본 베기 궤적
- 숙련 원형 베기
- 전진 검기
- 마무리용 넓은 궤적과 잔상
- 공용 타격 섬광과 먹빛·불꽃 파편

현재 64px 환도 4프레임은 레거시 참고 자료로 유지하되, 새 계약을 검증한 뒤 실제 사용 여부를 결정한다. 기존 환도 `MeleeArcComponent` 제외 경로와 `AttackEffectComponent` 도형 경로는 새 컴포넌트와 중복 렌더되지 않게 하나의 호출 경로로 통합한다.

### 6.3 표현 규칙

- 조선 민속 판타지의 먹선, 금빛·백색 칼빛, 절제된 붉은 충돌색을 사용한다.
- 굵은 외곽선과 2–3단계 셀 셰이딩을 유지한다.
- 검신 자체보다 이동 궤적과 타격 방향이 먼저 읽혀야 한다.
- 회전 시 텍스트, 문양, 광원 방향이 부자연스럽게 뒤집히지 않도록 대칭 가능 요소와 방향 전용 요소를 구분한다.
- 화면을 가리는 큰 불투명 면을 피하고 알파가 빠르게 감쇠하도록 한다.

## 7. 에셋 제작·보관 계약

### 7.1 스타일

기존 승인 방향을 유지한다.

- 128px 기준의 3–4등신 캐릭터
- 굵고 명확한 외곽선
- 2–3톤 셀 셰이딩
- 조선 복식, 목재, 한지, 단청, 먹, 부적과 무속 문양 어휘
- 캐주얼 일러스트 가독성과 민속 판타지 분위기의 균형

VFX는 작은 화면에서도 형태가 읽히도록 실루엣과 명암 대비를 우선한다.

### 7.2 디렉터리

- `art_source/generated/`: 생성 원본과 고해상도 중간 결과. `pubspec`에 등록하지 않는다.
- `assets/images/vfx/`: 베기, 충돌, 오라, 상태, 적 위험 효과.
- `assets/images/projectiles/`: 플레이어·적 투사체와 충돌 시트.
- `assets/images/zones/`: 장판, 결계, 예고 영역.
- `assets/images/enemies/`: 적 4×4 애니메이션 시트.
- `assets/images/tiles/`: 바닥 타일과 변형.
- `assets/images/props/`: 무대 가장자리 장식과 장애물이 아닌 배경 소품.

### 7.3 제작 흐름

1. 이미지 생성 도구로 투명 배경의 독창적 고해상도 원본을 만든다.
2. 사람이 결과를 검사해 상업 작품 모사, 깨진 해부, 잔류 문자, 불필요한 배경을 제외한다.
3. 크롭, 투명 여백, 프레임 정렬, anchor, 색 공간과 알파를 정규화한다.
4. 런타임용 RGBA PNG 또는 스프라이트 시트로 내보낸다.
5. 프레임 수·셀 크기·알파·경로·anchor 계약 테스트를 통과시킨다.
6. VFX 갤러리에서 방향, 밝고 어두운 배경, 배율, 반복을 확인한다.
7. 실제 전투 컴포넌트에 연결해 판정 방향과 충돌 타이밍을 확인한다.
8. SHA-256, 생성 방식, 검토 상태, 런타임 사용처를 권리·상태 장부에 기록한다.

에셋 내부에 한글·영문을 포함한 텍스트를 구워 넣지 않는다. UI 라벨은 Flutter 텍스트 레이어로 유지한다.

### 7.4 제작 순서

1. 환도 기본·숙련 원형·검기·마무리·충돌
2. 봉인베기, 바람·번개 부채, 신기전, 장승 영역, 오색 결계, 서리 장판, 부적
3. 적 독·충격파·비명·공격 예고·투사체·방패 반응
4. 무대 타일·변형·데칼·가장자리 소품
5. 누락된 적 8종의 4×4 시트

각 묶음은 이미지 검토를 통과한 뒤에만 런타임 레지스트리에 일괄 등록한다.

## 8. 다른 무기와 적 VFX

환도에서 검증된 이벤트·레지스트리 계약을 재사용하되 공격 유형별로 시각 문법을 분리한다.

- 봉인베기: 부적·봉인선이 베기 방향을 보강하고 충돌 시 짧게 잠긴다.
- 바람·번개 부채: 부채꼴 도형 대신 바람 결, 구름, 번개 갈래가 범위를 읽게 한다.
- 신기전: 화살 본체, 불꽃 꼬리, 충돌 파편을 분리한다.
- 장승·오색 결계·서리: 바닥 문양과 가장자리 맥동을 분리해 캐릭터가 묻히지 않게 한다.
- 부적: 대상 anchor에 붙는 표식과 전이 궤적을 분리한다.
- 적 위험 효과: 준비 단계는 낮은 불투명도와 명확한 가장자리, 판정 단계는 짧은 고대비 효과로 구분한다.
- 방패: 방향 표식, 막기 순간, 파괴 또는 해제 상태를 서로 다른 프레임으로 표현한다.

적 예고의 실제 안전·위험 경계는 게임플레이 형상에서 가져온다. 장식 이미지의 시각적 외곽이 판정보다 좁아 플레이어를 속이지 않도록 한다.

## 9. 무대 타일·데칼·소품

무대는 코드로 그린 단색 바닥을 최종 표현으로 사용하지 않는다. 별도 패키지 없이 Flame의 정적 chunk 또는 `SpriteBatch`로 구성한다.

- 기본 바닥 타일과 2–4개의 미세 변형을 준비한다.
- 시드 기반으로 변형, 좌우 반전, 허용된 회전을 결정해 매 실행의 재현성을 유지한다.
- 흙 얼룩, 낙엽, 종이 조각, 금 간 돌과 같은 데칼을 낮은 밀도로 배치한다.
- 장승, 기와 파편, 등롱, 풀과 같은 비충돌 소품은 전투 중심을 가리지 않도록 가장자리 밀도를 높인다.
- 타일과 데칼은 스테이지 생성 시 배치하고 매 프레임 생성·삭제·업데이트하지 않는다.
- 충돌 판정이 필요한 오브젝트는 이번 장식 레이어와 분리한다.

시각적 반복이 두드러지지 않는 최소 에셋 수를 먼저 검증하고, 성능 측정 없이 변형 수를 늘리지 않는다.

## 10. 누락 적 8종

각 적은 고유 실루엣과 색상 단서를 가져야 하며 기존 적 시트를 복사해 이름만 바꾸지 않는다. 공통 계약은 128px 셀 기반 4×4, 투명 RGBA, 일관된 발 anchor이다.

- 0–3: 이동
- 4–7: 공격
- 8–9: 피격
- 10–15: 사망

시트 제작 전 각 적의 실루엣, 주색, 무기·소품, 공격 방향을 한 줄 명세로 확정한다. 정규화 후 `EnemySpriteSheet.specs`와 `AssetCatalog`가 같은 경로·프레임 계약을 사용하도록 갱신한다. 누락 프레임이나 잘못된 크기는 계약 테스트에서 실패해야 한다.

## 11. 개발 전용 VFX 갤러리

갤러리는 `kDebugMode`에서만 접근 가능한 개발 화면으로 만든다. 별도 모형 렌더러를 만들지 않고 `AttackVisualRegistry`와 실제 전투 컴포넌트를 호출한다.

필수 조작은 다음과 같다.

- 0.25×, 0.5×, 1× 재생 속도
- 한 번 재생과 반복
- 8방향 선택
- 밝은 배경과 어두운 배경
- 기준 캐릭터 표시
- 판정 형상 표시 토글
- anchor와 pivot 표시
- 현재 프레임 인덱스
- 활성 컴포넌트 수

갤러리의 완료 조건은 실제 전투 경로와 동일한 에셋 키, 수명 주기, 방향 변환을 사용하는 것이다. 갤러리 전용 가짜 효과로 통과시킬 수 없다.

## 12. 성능 측정과 최적화

### 12.1 두 종류의 기준선

결정론적 300초 호스트 시뮬레이션은 로직 부하, 개체 수, 컴포넌트 잔류, 처리 시간 비교에 사용한다. 결과의 FPS는 고정 `dt` 기반 논리 FPS로 명시한다.

로컬 Chrome profile 측정은 60–90초 동안 다음 렌더 지표를 수집한다.

- 프레임 시간 p50, p95, p99
- 33ms 초과와 50ms 초과 프레임 수
- build와 raster 구간
- 첫 이미지 로드·디코딩 시점
- 컴포넌트 생성·제거율
- 구간별 적, 투사체, 효과 컴포넌트 수

두 측정은 같은 시드와 가능한 한 같은 전투 구간을 사용하되 서로 다른 지표임을 보고서에서 분리한다.

### 12.2 최적화 순서

측정 근거가 있는 항목을 다음 순서로 처리한다.

1. 전투 에셋 선로딩으로 첫 사용 로드 제거
2. 반복적인 루트 `children` 탐색을 명시적 인덱스나 카운터로 축소
3. 환도 구·신 VFX의 중복 생성 제거
4. 완료 컴포넌트와 retained owner를 정확히 제거·계측
5. 정적 타일과 데칼 배치의 batch 처리
6. 반복 생성되는 `Paint`, `Path`, `Sprite` 캐시

공간 분할과 대규모 풀링은 재측정 결과 O(P×E), O(E²), 생성·수거 비용이 실제 병목으로 확인될 때만 도입한다. 구조 복잡도만 늘리는 선제 최적화는 하지 않는다.

부적 부착 맵을 포함해 모든 retained owner가 계측 대상에 들어가야 한다. 컴포넌트가 제거되어도 별도 맵이나 목록이 참조를 보유하는 상태 누수를 검사한다.

### 12.3 환경 실패 처리

셰이더 컴파일 SIGSEGV처럼 앱 코드 실행 전 발생한 실패는 환경 장애로 별도 기록한다. 이를 앱 회귀 또는 통과로 간주하지 않는다. 재현 명령, Flutter 버전, 실패 셰이더와 스택을 남기고 가능한 우회 환경에서 관련 테스트를 계속한다.

## 13. 정리와 삭제 정책

삭제 전 감사 문서를 만든다. 각 후보에 대해 다음을 기록한다.

- 경로와 SHA-256
- 정적 코드 참조
- 동적 경로 조합 가능성
- `pubspec` 등록 여부
- 테스트·문서 참조
- 대체 에셋
- 삭제 또는 보류 이유

권리 원본과 생성 원본은 런타임에서 사용하지 않는다는 이유만으로 삭제하지 않는다. 동적 참조 가능성이 있거나 용도가 불명확한 파일은 보류한다. 중요한 대량 삭제는 구현 변경과 분리하고 정확한 대상 목록을 제시해 사용자 확인을 받은 뒤 수행한다.

완성된 새 경로가 안정화된 후 다음을 제거 후보로 삼는다.

- 환도 구 도형 렌더 경로
- 정상 경로를 가리는 조용한 fallback
- 전투 중 개별 이미지 로드
- 갤러리 전용 중복 효과
- 완전히 대체되고 참조가 없는 임시 에셋

## 14. UI 이미지화 공백 감사

전투 VFX 작업과 별도로 로비, HUD, 패널, 버튼, 아이콘, 배경에서 코드 도형 또는 임시 아틀라스를 사용하는 위치를 목록화한다. 각 항목은 `완료`, `이미지 있음/미연결`, `임시 이미지`, `도형 주표현`, `보조 도형 허용`으로 분류한다.

이번 범위에서는 전투 판독성과 직접 연결되는 HUD·상태 아이콘의 누락만 수정 후보로 올린다. 전면 UI 재디자인은 감사 결과와 우선순위를 사용자에게 제시한 뒤 후속 작업으로 분리한다.

## 15. 작업 분배와 파일 소유권

메인 `gpt-5.6-sol` 에이전트가 범위, 설계, 통합, 최종 판단을 소유한다. 서브에이전트는 반드시 명시된 Terra 또는 Luna 모델을 사용하고 Sol을 상속하지 않는다.

- `explorer` / Luna / read-only: 관련 경로와 심볼, 원인 후보, 수정 파일 목록만 조사한다.
- `ui_designer` / Terra / read-only: 화면 구조, 에셋 크기, 레이어와 아트 명세를 검토한다.
- `flutter_worker` / Terra / workspace-write: 메인이 승인한 파일 범위의 Flutter·Flame 코드만 수정하고 관련 테스트만 실행한다.
- `qa` / Luna / 기본 read-only: 테스트 선택, 로그 분석, 재현 절차와 수동 확인 항목을 작성한다.
- `reviewer` / Terra / read-only: 통합된 최종 diff를 구현 완료 후 한 번만 검토한다.

기본 동시 실행 수는 2이고 큰 작업에서 최대 3이다. 명백히 독립적인 읽기 작업만 병렬로 수행하며 동일 파일을 두 쓰기 에이전트에 배정하지 않는다. 각 에이전트는 관련 파일과 좁은 완료 조건만 받는다. 복잡한 설계 변경이나 해결이 어려운 오류는 서브에이전트가 임의로 결정하지 않고 근거와 선택지를 메인에 반환한다.

## 17. 검증 전략

각 마일스톤에서는 변경 파일과 직접 관련된 테스트, 분석, 갤러리·실전 수동 확인만 실행한다. 전체 테스트와 웹 빌드를 중복 실행하지 않는다.

자동 검증 대상은 다음과 같다.

- 레지스트리의 모든 경로가 존재하고 `pubspec` 범위에 포함되는지
- PNG가 RGBA이고 기대 크기·셀 수·프레임 수를 갖는지
- 필수 프레임에 유효 알파 픽셀이 있는지
- anchor, pivot, 프레임 순서와 방향 규칙이 등록되었는지
- 개발 상태가 `missing`인 효과가 릴리스 완료 목록에 섞이지 않는지
- 동일 공격에서 구·신 VFX가 동시에 생성되지 않는지
- 피해 판정 데이터와 시각 이벤트의 원점·방향·형상이 동일한지
- 효과 종료 후 컴포넌트와 retained owner가 기준 수준으로 돌아오는지
- 누락 적 8종의 상태 프레임 범위가 공통 계약과 맞는지
- 정적 무대가 매 프레임 타일 컴포넌트를 생성하지 않는지

수동 확인은 밝고 어두운 배경, 8방향, 저속 재생, 다수 적 중첩, 화면 가장자리, 숙련·시너지 단계, 첫 전투 진입을 포함한다.

최종 통합 후에만 다음을 한 번 수행한다.

1. `flutter analyze`
2. 전체 `flutter test`
3. Flutter web build

Android/iOS 빌드와 실제 기기 성능 검증은 사용자가 별도로 요청하거나 기기를 제공할 때 수행한다.

## 18. 오류 처리와 회귀 방지

- 에셋 선로딩 실패는 실패한 경로와 `effectId`를 함께 보고한다.
- 개발 빌드는 누락을 눈에 띄게 표시하며 예외를 조용히 삼키지 않는다.
- 릴리스 안전 fallback은 게임플레이를 계속하기 위한 최소 표현만 사용하고 원인을 로그에 남긴다.
- 이미지 크기·프레임 계약 오류는 런타임 전 테스트에서 실패시킨다.
- VFX 컴포넌트 제거 시 타이머, 자식 컴포넌트, 별도 소유 맵을 함께 정리한다.
- 성능 개선은 변경 전후 동일 시드 지표로 판단한다.
- 밸런스 데이터 diff가 발생하면 시각 개선과 분리해 되돌리거나 사용자 승인을 받는다.

## 19. 완료 기준

이 설계의 구현은 다음이 모두 충족될 때 완료로 판단한다.

- 문서화된 도형 주표현 목록이 이미지 VFX 또는 명시적 보류 상태를 갖는다.
- 환도베기가 모든 단계에서 실제 PNG/스프라이트를 사용하고 판정 방향·타이밍과 일치한다.
- 플레이어·적 효과의 레지스트리와 선로딩 경로가 실전과 갤러리에서 동일하다.
- 무대가 이미지 타일·데칼·소품으로 구성되고 정적 batch 전략을 따른다.
- 누락된 적 8종이 고유 시트와 런타임 등록을 갖는다.
- 권리·상태 장부와 SHA-256 기록이 최신이다.
- 성능 보고서가 논리 FPS와 실제 렌더 지표를 구분한다.
- 완료 컴포넌트와 retained owner의 누수가 없다.
- 사용자 확인 없이 모호하거나 중요한 에셋을 삭제하지 않았다.
- 최종 reviewer가 통합 diff를 한 번 검토했고 메인 Sol이 최종 검증을 한 번 수행했다.

## 20. 위험과 의사결정 보류

- 이미지 생성 결과는 반복 수정이 필요할 수 있다. 첫 생성물을 자동 승인하지 않는다.
- 128px 시트의 메모리 사용량은 실제 적 동시 등장 집합과 선로딩 범위를 기준으로 측정한다.
- 모든 효과를 8방향 전용 이미지로 만들지, 회전 가능한 공용 이미지와 혼합할지는 환도 갤러리 결과로 결정한다.
- 공간 분할과 풀링은 현재 설계의 필수 조건이 아니며 재측정 결과로 결정한다.
- 실제 모바일 성능 목표는 기기와 빌드 모드가 정해진 뒤 별도 승인한다.
- UI 전면 재디자인 범위는 이번 감사 결과를 보고한 뒤 사용자가 선택한다.
