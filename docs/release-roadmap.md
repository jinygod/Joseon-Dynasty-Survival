# 조선 왕조 서바이벌 완성·출시 로드맵

## 1. 현재 판단

현재 빌드는 **핵심 전투가 성립하는 5분 싱글플레이 알파**다. 웨이브, 적 4종, 보스 1종, 무기 4종, 증강, 레벨업, 런 결과, 해금·저장 시스템까지 이어지는 한 판의 구조는 완성되어 있다.

2026-07-14 기준 확인 결과:

- `dart analyze`: 문제 없음
- `flutter test`: 82개 테스트 통과
- `flutter build web`: 영문 드라이브 매핑 환경에서 성공
- 최종 이미지 자산: 없음. 등록된 7개 파일은 모두 `.gitkeep`
- 오디오 시스템 및 음원: 없음
- Android 릴리스 서명과 고유 애플리케이션 ID: 미설정
- 구현 코드는 `codex/pixel-survivor-mvp` 브랜치에 있고 `master`에는 아직 통합되지 않음

따라서 지금 바로 콘텐츠 수를 늘리는 것보다, 현재 5분 빌드를 반복해서 하고 싶을 만큼 손맛과 가독성이 좋은 **폴리시드 세로 슬라이스**로 만드는 것이 최우선이다.

## 2. 출시 원칙

1. 기능 수보다 한 판의 재미와 조작감을 먼저 완성한다.
2. 임시 도형·개발자 UI가 남은 상태에서는 콘텐츠 제작량을 늘리지 않는다.
3. 신규 콘텐츠는 기존 한 판이 재미있다는 플레이테스트 근거가 생긴 뒤 추가한다.
4. 모든 단계는 느낌이 아니라 통과 조건으로 종료한다.
5. 1차 출시 플랫폼은 Android를 기본 가정한다. iOS, Windows, Steam은 별도 출시 트랙으로 다룬다.

### 4.1 개발 기준선 고정

- [ ] `codex/pixel-survivor-mvp`의 구현을 검토한 뒤 기본 브랜치에 통합한다.

- [x] 한글 경로에서 Flutter 셰이더 컴파일러가 충돌하는 문제를 피하도록 CI는 영문 경로를 사용한다.
- [x] 웹 빌드의 Cupertino 폰트 경고 원인을 제거한다.
- [x] `pubspec.yaml`의 이름, 설명, 버전 정책을 알파 제품 값으로 바꾼다.
- [ ] 저장 데이터에 스키마 버전을 넣고 이후 업데이트의 마이그레이션 규칙을 정한다.
- [x] 자동 테스트와 웹 빌드를 묶은 로컬 릴리스 체크 스크립트를 만든다. Android SDK가 준비된 환경에서는 `-IncludeAndroid`로 APK 빌드까지 실행한다.

완료 기준: 깨끗한 환경에서 한 명령으로 의존성 설치, 분석, 테스트, 빌드가 재현된다.

### 4.2 현재 5분 전투의 재미 검증

- [ ] 초반 30초 안에 이동, 자동 공격, 경험치 획득, 레벨업의 재미를 모두 보여준다.
- [ ] 0~1분은 학습, 1~3분은 빌드 형성, 3~4분 30초는 압박 상승, 이후는 보스 결전이라는 리듬을 플레이테스트로 확인한다.
- [ ] 무기 4종이 그래픽을 가려도 공격 방식과 선택 이유가 분명하도록 차이를 강화한다.
- [ ] 각 레벨업 선택지가 실제 플레이 스타일을 바꾸고, 단순 수치 증가만 반복되지 않도록 조정한다.
- [ ] 경험치 곡선, 적 체력, 적 수, 피해량, 보스 체력과 공격 주기를 실제 플레이 데이터로 조정한다.
- [ ] 초보자, 장르 경험자, 숙련자 그룹별 승률과 사망 구간을 기록한다.
- [ ] 무기별 선택률, 최종 레벨, 피해 비중, 승률을 기록할 수 있는 개발용 런 로그를 추가한다.
- [ ] 무적 시간, 피격 판정, 넉백, 화면 흔들림, 피해 숫자가 과하거나 답답하지 않은지 조정한다.
- [ ] 보스 경고 표시가 모든 화면 크기에서 충분히 읽히고 회피할 시간을 주는지 검증한다.
- [ ] 20회 이상 내부 플레이테스트와 10명 이상 외부 플레이테스트를 수행한다.

완료 기준:

- 외부 플레이어 80% 이상이 별도 설명 없이 첫 판을 끝까지 진행한다.
- 첫 판 종료 후 60% 이상이 즉시 한 번 더 플레이하고 싶다고 답한다.
- 특정 무기 또는 증강 하나가 승리 빌드를 독점하지 않는다.
- 억울하다고 느끼는 피격, 보이지 않는 위험, 선택 불가 상태가 재현되지 않는다.

### 4.3 임시 그래픽 제거

- [ ] 최종 아트 방향, 색상 팔레트, 픽셀 해상도, 외곽선, 광원 규칙을 1페이지 가이드로 고정한다.
- [ ] 플레이어 걷기·피격·사망 애니메이션을 제작한다.
- [ ] 일반 적 4종과 보스의 이동·공격·피격·사망 애니메이션을 제작한다.
- [ ] 무기 4종의 발사체, 근접 궤적, 폭발, 부적 연결 효과를 제작한다.
- [ ] 경험치 보석, 피격 섬광, 위험 범위, 보스 경고 효과를 제작한다.
- [ ] 반복 가능한 스테이지 타일, 배경 장식, 충돌 없는 시각 레이어를 제작한다.
- [ ] 무기·증강·해금 아이콘과 HUD 프레임을 제작한다.
- [ ] 메인 메뉴, 레벨업, 결과 화면을 같은 아트 스타일로 통일한다.
- [ ] 화면에 적과 효과가 몰려도 플레이어, 경험치, 위험 공격이 우선 보이도록 렌더 우선순위를 조정한다.
- [ ] AI 생성 자산은 사용 권리, 생성 기록, 후처리 담당, 원본 파일을 함께 보관한다.

완료 기준: 개발자 설명 없이 캡처 한 장만 보고 플레이어·적·투사체·위험 범위·경험치를 모두 구분할 수 있다.

### 4.4 사운드와 전투 피드백

- [ ] 배경 음악 재생, 루프, 볼륨 저장 시스템을 추가한다.
- [ ] 일반 전투, 보스전, 승리, 패배 음악을 준비한다.
- [ ] 무기 4종에 서로 구분되는 공격음을 적용한다.
- [ ] 피격, 치명타, 적 사망, 보석 획득, 레벨업, 버튼, 보스 경고, 승패 효과음을 적용한다.
- [ ] 동시 발음 수 제한, 반복음 피치 변화, 거리 또는 중요도 기반 우선순위를 적용한다.
- [ ] 진동 지원 기기에서는 강한 피격, 레벨업, 보스 공격에 선택적 햅틱을 적용한다.
- [ ] 음악, 효과음, 진동을 각각 끌 수 있게 한다.

완료 기준: 화면을 보지 않아도 공격 성공, 피격, 레벨업, 보스 위험, 승패를 소리로 구분할 수 있고 소리가 겹쳐 깨지지 않는다.

## 5. P1 — 제품으로 완성하기

### 5.1 조작과 접근성

- [ ] 현재 개발자 이동 패드를 실제 모바일 가상 스틱으로 교체한다.
- [ ] 스틱 위치·크기·데드존을 다양한 손 크기와 화면 비율에서 검증한다.
- [ ] 터치가 끊겼을 때 이동 입력이 남지 않도록 처리한다.
- [ ] Android 뒤로가기, 앱 전환, 화면 잠금 시 자동 일시정지를 지원한다.
- [ ] 키보드와 게임패드를 지원할 플랫폼에서는 입력 매핑과 버튼 안내를 제공한다.
- [ ] 화면 흔들림 강도, 피해 숫자, 진동, UI 크기 옵션을 제공한다.
- [ ] 색만으로 희귀도, 위험, 체력을 구분하지 않도록 모양과 명암 차이를 함께 사용한다.

### 5.2 전체 화면 흐름

- [ ] 로고와 로딩 화면을 추가한다.
- [ ] 메인 메뉴에 시작, 계속, 해금/도감, 설정, 크레딧, 종료 흐름을 구성한다.
- [ ] 캐릭터 선택 화면에서 능력, 시작 무기, 해금 조건을 보여준다.
- [ ] 스테이지 선택과 난이도 또는 권장 정보 표시를 추가한다.
- [ ] 첫 실행 튜토리얼에서 이동, 자동 공격, 경험치, 레벨업, 보스 경고를 짧게 안내한다.
- [ ] 게임 중 일시정지, 설정, 재시작, 메인 메뉴 복귀를 제공한다.
- [ ] 결과 화면에 이번 판의 핵심 기록, 새 해금, 최고 기록, 재도전 동기를 보여준다.
- [ ] 모든 문구를 한국어로 통일하고, 영어가 필요하면 문자열 리소스를 분리해 언어를 명시적으로 선택한다.
- [ ] 문서와 소스의 깨진 한글 표시를 전수 점검한다.

### 5.3 최소 1.0 콘텐츠

완성도를 지키기 위한 권장 최소 범위다. 이보다 많이 만드는 것은 이 범위를 모두 폴리시한 뒤 결정한다.

- [ ] 플레이 가능한 캐릭터 3명: 서로 다른 시작 무기와 고유 패시브
- [ ] 무기 8종: 근접, 직선, 추적, 범위, 방어형 등 역할 분리
- [ ] 증강 16종 이상: 공격, 생존, 이동, 획득, 조건부 위험 보상 빌드 지원
- [ ] 무기별 최종 진화 또는 강한 5레벨 정체성 1개
- [ ] 일반 적 8종 이상: 속도, 진형, 돌진, 원거리, 방어, 소환 역할 분리
- [ ] 엘리트 변형 3종 이상
- [ ] 스테이지 2개: 시각 테마와 웨이브 구성이 실제로 다름
- [ ] 보스 3종: 각자 최소 3개 공격 패턴과 광폭화 단계
- [ ] 해금 목표 15개 이상과 도감/진행률 화면
- [ ] 일반 런 8~12분 또는 현재 5분 속도전 모드 중 제품 정체성에 맞는 하나를 주력 모드로 확정

제외 권장: 1.0 이전 온라인 협동, 광고, 상점 경제, 일일 과제, 라이브 서비스. 이 기능들은 코어 재미 검증을 늦추고 QA 범위를 크게 늘린다. 로컬 2인 협동도 1.0 이후 별도 프로젝트로 다룬다.

출시 차단 기준:

- 크래시, 진행 불가, 저장 소실: 0건
- 재현 가능한 심각한 프레임 정지: 0건
- UI 잘림, 버튼 입력 불가, 보이지 않는 공격: 0건
- 보통 등급 버그: 목록화하고 출시 승인자가 명시적으로 수용

## 7. P2 — Android 출시 준비

### 7.1 앱 패키징

- [ ] 최종 게임명과 영문명을 확정한다.
- [ ] 고유한 Android application ID를 확정하고 변경 후에는 유지한다.
- [ ] 릴리스 키스토어를 생성하고 안전하게 백업한다.
- [ ] 디버그 키가 아닌 릴리스 서명으로 AAB를 만든다.
- [ ] 앱 아이콘, 적응형 아이콘, 스플래시 화면을 최종 자산으로 교체한다.
- [ ] 최소/대상 Android 버전, 64비트 지원, 화면 방향 설정을 확인한다.
- [ ] 버전명, 빌드 번호, 변경 기록 규칙을 정한다.
- [ ] 난독화와 심볼 보관 정책을 정하고 크래시 역추적이 가능하게 한다.

### 7.2 스토어와 법적 자료

- [ ] 개발자 계정과 결제/세금 정보를 준비한다.
- [ ] 앱 설명, 짧은 설명, 키워드, 카테고리를 작성한다.
- [ ] 아이콘, 피처 그래픽, 실제 플레이 스크린샷, 짧은 트레일러를 제작한다.
- [ ] 지원 이메일, 웹페이지, 개인정보처리방침 URL을 준비한다.
- [ ] 수집 데이터가 없다면 스토어 데이터 안전성 양식에도 정확히 반영한다.
- [ ] 연령 등급 설문과 폭력 표현을 실제 게임 내용에 맞게 제출한다.
- [ ] 사용한 폰트, 음원, 효과음, 코드, AI 자산의 라이선스 장부와 크레딧을 완성한다.
- [ ] 게임명, 로고, 스토어 문구가 타인의 상표와 충돌하지 않는지 확인한다.

## 8. P2 — 소프트 론치

- [ ] 내부 테스트 트랙에서 개발팀 기기 설치와 업데이트를 검증한다.
- [ ] 비공개 테스트에 장르 초보와 숙련자를 모두 모집한다.
- [ ] 첫 실행 완료율, 첫 판 완주율, 첫 승리까지의 판 수, 재도전율, 캐릭터·무기 선택률을 측정한다.
- [ ] 크래시 없는 사용자 비율과 ANR을 확인한다.
- [ ] 피드백은 치명적 문제, 반복 불만, 개인 취향으로 분류한다.
- [ ] 밸런스 변경은 한 번에 한 축만 바꾸고 전후 데이터를 비교한다.
- [ ] 최종 출시 후보를 최소 3일간 심각한 문제 없이 유지한다.

권장 통과 기준:

- 크래시 없는 사용자 99.5% 이상
- 첫 실행 후 첫 판 진입 90% 이상
- 첫 판을 중도 이탈하지 않고 결과 화면까지 도달 75% 이상
- 두 번째 판 진입 50% 이상
- 저장 소실 및 결제 관련 문제 0건

## 9. P3 — 정식 출시와 운영

- [ ] 출시일, 가격 또는 무료 정책, 지원 언어, 지원 기기를 확정한다.
- [ ] 1.0 빌드를 잠그고 출시 직전에는 차단 버그만 수정한다.
- [ ] 스토어 심사 지연 또는 거절 사유에 대응할 여유를 둔다.
- [ ] 출시 공지, 트레일러, 커뮤니티 게시물, 프레스 키트를 준비한다.
- [ ] 첫 72시간 크래시, 리뷰, 지원 문의를 집중 모니터링한다.
- [ ] 저장·크래시 문제를 위한 핫픽스 브랜치와 배포 절차를 준비한다.
- [ ] 1.0 이후 2~4주 단위의 콘텐츠·밸런스 패치 원칙을 공개한다.
- [ ] 사용자 요청이 많아도 코어 밸런스와 성능을 해치는 기능은 별도 검증 후 추가한다.

## 10. 플랫폼별 추가 트랙

### iOS

- Mac과 Xcode, Apple Developer 계정, 인증서·프로비저닝, TestFlight 검증이 필요하다.
- 현재 `Info.plist`에는 세로 방향도 허용되어 있으므로 가로 전용 정책과 일치시켜야 한다.
- iPhone과 iPad의 안전 영역, 성능, 백그라운드 복귀를 별도로 검증한다.

### Windows/Steam

- Visual Studio C++ 데스크톱 도구, Windows 릴리스 빌드, 게임패드·키보드 UX가 필요하다.
- 창/전체 화면, 해상도, 그래픽 옵션, 저장 위치, Steam Deck 호환성을 검증한다.
- Steamworks 등록, 상점 페이지, 빌드 depot, 도전 과제, 클라우드 저장은 별도 범위로 계획한다.

### Web

- 현재 영문 경로 매핑에서는 빌드되지만, 모바일 정식판의 주 플랫폼으로 간주하지 않는다.
- 체험판 배포에 쓸 경우 로딩 크기, 브라우저 호환성, 포커스 이탈, 저장소 제한을 별도 검증한다.

## 12. 1.0 완료 정의

다음 조건을 모두 충족해야 “게임 완성”으로 본다.

- 핵심 런이 처음부터 끝까지 재미와 긴장 곡선을 유지한다.
- 임시 도형, 임시 문구, 개발자용 조작 UI가 남아 있지 않다.
- 그래픽, 애니메이션, 음악, 효과음, 햅틱이 일관된 스타일로 완성되어 있다.
- 튜토리얼, 설정, 일시정지, 캐릭터·스테이지 선택, 결과, 해금 흐름이 완성되어 있다.
- 최소 출시 콘텐츠가 모두 서로 다른 플레이 경험을 제공한다.
- 자동 테스트, 통합 테스트, 실제 기기 QA가 통과한다.
- 목표 기기에서 성능 예산을 지키고 크래시·저장 소실·진행 불가 버그가 없다.
- 서명된 릴리스 빌드, 스토어 자료, 개인정보·라이선스 문서가 완성되어 있다.
- 비공개 테스트 지표가 소프트 론치 통과 기준을 만족한다.
- 출시 후 모니터링, 지원, 핫픽스 절차가 준비되어 있다.
